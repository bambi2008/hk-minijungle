# External production acceptance

This document is the execution boundary for the five items that cannot be proved by local UI or SQLite smoke tests: managed PostgreSQL, real devices, enterprise identity, backup/restore and customer field operations.

## Order

1. Provision a managed PostgreSQL database with TLS, private networking, PITR and an application role. Apply `infra/postgres/001_runtime_schema.sql` through `018_health_esg_operational_ledger.sql` in numeric order, then run `npm.cmd run production:preflight -- --url https://<production-host> --bearer-token <short-lived-token> --strict`.
2. Configure the real OIDC issuer, JWKS URL and audience. Obtain short-lived tokens for Platform Admin, FM Lead and two different client viewers. Run `npm.cmd run probe:oidc -- --strict` for discovery/JWKS/token reachability, then `node scripts/oidc-role-scope-acceptance.mjs --strict` with those four tokens and client IDs. The matrix checks roles, permissions, portfolio access and cross-client asset isolation; MFA enrollment, role transitions and revocation still require a dated IdP-admin acceptance test.
3. Register one physical gateway/sensor and one physical camera in the platform. Use `npm.cmd run probe:device -- --kind reading --allow-write` with the real device ID/key/module/wall values, then run it again with `--kind camera --file <real-image> --allow-write`. Keep both JSON outputs as release evidence. The probe writes one real reading and one real camera capture.
4. Create an encrypted PostgreSQL archive with `npm.cmd run backup:postgres -- --out <backup-directory> --upload`. The upload path reads both the encrypted archive and manifest back from object storage and compares bytes and SHA-256 values. Run `npm.cmd run restore:postgres -- --from-offhost --verify-only` for remote archive verification, then restore that remote copy to a separately provisioned isolated database using `--from-offhost --target-url <isolated-database-url>`. Keep the restore JSON output; the script rejects the source target.
5. Export actual completed Airtable/technician records to the CSV header in `docs/templates/customer-field-cycle-evidence.template.csv` (or the JSON shape in `docs/templates/customer-field-cycle-evidence.example.json`). Each row needs cycle ID, client ID, work-order ID, module ID, technician ID, service time, status, duration and at least one `https://`, `s3://` or `evidence://` proof reference. Run `npm.cmd run validate:field-evidence -- --input <cycles.csv> --format csv --out <field-report.json> --strict`. The validator requires at least two completed cycles for each of at least two clients.
6. Run the acceptance aggregator with all reports: `npm.cmd run production:acceptance -- --url https://<production-host> --bearer-token <short-lived-token> --identity-report <identity.json> --device-reading-report <reading.json> --device-camera-report <camera.json> --backup-manifest <backup-directory>/manifest.json --restore-report <restore.json> --field-evidence <field-report.json> --strict`.

The aggregator is a release candidate report, not a score generator. It reports `candidate` only when all five technical/data gates pass. The official production operations score remains **65%** until the evidence is independently reviewed and the repeated operating cycles are accepted. Do not change the `DR_FOREST_*_VERIFIED` markers by hand to make a report pass.
